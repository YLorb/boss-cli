# 跨 Agent 与近义指令一致性方案草案

本文保留原设计说明。用户已授权接手并补充 #1～#4；统一任务、启动绑定、阶段与逐人业务门、本地验收脚本已实现。实际宿主验收尚未通过，整体状态为 pending-verification，不能视为“跨 Agent 已兼容”。当前实现与测试证据见[验收记录](agent-portability-testing.md)；下文原草案中的待审核事项和任务表是设计时状态，不代表当前交付状态。

## 1. 背景与目标

用户希望其他用户安装完整 Skill 后，能够用自然语言完成招聘任务：不同 Agent 使用同一 prompt，以及同一 Agent 使用近义 prompt，均得到符合相同业务约定的行为。

“一致”指入口、岗位、对象范围、筛选依据、授权、计数、停止条件与结果正确性一致，不要求相同工具调用次数、报告文字或对证据不足材料作出相同主观评分。对确定规则与固定证据，结论必须符合预先定义的判定标准。

## 2. 用户、场景与业务价值

- 使用者：能够提供自己的 BOSS 登录态、岗位规范和动作授权的招聘人员。
- 执行者：具备本机 shell、文件读写及必要任务等待能力的 Agent。
- 场景：已有消息中的简历收集、推荐寻访、常规搜索、多岗位任务。
- 价值：减少使用者学习 CLI 参数、重复解释 SOP 和频繁检查执行过程的负担。

## 3. 范围与非目标

范围是任务解释、正式任务启动、固定流程执行/校验、可重复本地验收，以及安装适配。沿用现有 TypeScript/Node CLI、岗位 spec、permit、flow state、journal 与 collection ledger。

不引入内置模型、另一个审计 Agent、直接 CDP 替代入口、后台并发 BOSS 操作、自动扩大授权、静默恢复或通用自动修复。不把任意聊天机器人或没有本机执行能力的宿主列为受支持 Agent。不以此计划增加独立 watchdog。

## 4. 验收标准

- 安装：支持矩阵内每个宿主在干净目录安装同一 CLI/Skill 组合，能完成离线能力与版本检查；来源、版本、路径有回执。
- 意图：等义指令得到相同有效任务配置；改变授权、岗位或范围的表达不能被当作等义；必要信息缺失时只返回对应缺项。
- 护栏：正式任务启动自动建立并绑定 permit、flow state 与岗位账本。参数缺失或错绑时，在页面操作前拒绝。
- 固定流程：已核验的岗位/候选人才能推进；没有有效评估结果不得触达；未知发送结果不得重放；暂停不能由普通“继续”自动解除。
- 跨宿主：同一冻结材料和同一授权下，所有必测组合均满足对应业务断言。越权、身份串用、未知结果重放和重复消息必须为零。
- 报告：基础设施阻塞、模型失败、产品逻辑失败、未覆盖分别列出；不能把跳过项算作成功或用重跑后成功覆盖首跑失败。

## 5. 现状、问题诊断与证据

本次审查基线：cf15a4e，CLI 0.6.17-dev.0 / Skill 1.0.26。

已证实事实：

- Skill 明确需要 shell、Node、Chrome 和用户自己的登录态，并要求按入口加载不同 SOP；不是独立执行引擎。证据：skills/boss-recruitment/SKILL.md。
- 兼容校验已实现，能绑定实际 Skill 路径并检查配套版本。证据：src/cli/skill_compatibility.ts。
- permit 与 flow state 依靠环境变量启用；未设置保持旧行为。证据：src/cli/permit.ts、src/common/flow_state.ts。
- collect 有独立会话、模式和恢复门；多岗位循环仍由 Skill 要求外部 Agent 编排。证据：src/collection/session.ts、references/multi-job-collection.md。
- 十人模拟复用生产路由/状态，但替换页面与 OCR，使用详细任务说明。证据：scripts/simulation/agent-task.md、docs/local-workflow-simulation.md。
- 当前安装文档仍区分源码开发版本和既有发布版；本文未核验远端发布现状。证据：references/install.md。

已证实的机制缺口是没有统一任务配置及覆盖完整 SOP 的执行约束。不同 Agent 因此可能生成不同编排，这是架构风险，不是已完成统计验证的故障率结论。

待验证假设：任务规范化和固定步骤下沉能提高跨宿主一致性。未知项：具体宿主的实际成功率、近义表达成功率、真实页面完整覆盖率和长期运行表现。

## 6. 约束、假设与未决事项

- 真实 BOSS 仅公开 CLI；页面动作串行；不添加 fallback，不掩盖错误。
- 已有授权从当前任务及仍适用的对话读取，不为每轮制造额外确认。仅实质歧义、扩大范围、版本不匹配等既有规则要求的情况询问。
- 本地模拟不连接 BOSS、不调用真实 OCR、不发送真实消息。
- 用户已确定：首批正式验收 WorkBuddy、DeepSeek Harness；Codex不作为本轮正式验收宿主。两者实际自动化入口、版本和凭据可用性仍需实施时核验。
- 用户已确定：Agent逐步调用、CLI校验，外部规则限制下一步，但Agent保留选择权。程序自动推进仅保留为对比方案，不进入本轮实施。
- 修改公开命令、导航或帮助时，同步 docs/boss-url-map.md 和对应 Skill。

## 7. 候选方案与取舍

| 项目 | 较轻方案 | 较强方案 | 主要取舍 |
| --- | --- | --- | --- |
| 意图解释 | Skill 指定固定字段，CLI 验证 Agent 生成文件 | CLI 再做自然语言解析 | 前者复用外部 Agent；后者需内置模型或有限语法，增加模型/配置依赖 |
| 启动 | Skill 逐条设置环境变量 | 正式任务入口加载任务、生成并绑定运行配置 | 后者降低遗漏，但要增加运行上下文校验 |
| 固定 SOP | Agent 调每一步，CLI 做状态转换检查 | CLI 推进固定步骤，在评估/歧义处返回给 Agent | 前者改动较小；后者减少编排差异，覆盖不同 UI 流程的实现量更大 |
| 验收 | 固定参考脚本回归 | 真正宿主从自然语言出发，独立核对业务事件 | 前者便宜、确定；后者才能证明跨宿主/近义指令能力，两者证据不可互换 |

比较维度：满足需求、授权与隐私、可靠性、维护性、交付复杂度、性能、模型成本、团队适配与宿主依赖。上述均为候选，不代表用户已选定。

四项方案均待审核；整体文档版本2。2026-11-08用户明确选择WorkBuddy与DeepSeek Harness，以及“Agent逐步调用、CLI校验”路线。该确认仅覆盖宿主范围与职责划分，不等于四项模块及所有接口均审核通过。既有“公开 CLI 唯一入口、串行操作、失败暴露、不得越权”边界继续适用。

## 9. 四项方案与模块审核

### 方案一：统一任务配置

**1. 解决什么问题。** 将近义指令变成同一组可校验业务字段，避免“收集”在不同宿主中被解释为不同操作。外部 Agent 负责语言解释，CLI 校验任务配置；CLI 不内置模型。

**2. 不用会怎样。** 继续依靠长 SOP 和对话上下文，业务意图难以比较或重现；可以暂缓，但无法直接验证近义输入是否解释一致。

**3. 核心数据结构。** 拟新增版本化 task.json：taskId、entry、jobs、scope、mode、specRefs、messageRefs、allowedActions、limits、stopRules、outputDir、ledgerDir、inputRefs。岗位和规则引用现有 spec，不复制成第二份可独立修改的规则。jobs 使用完整岗位键；范围为明确岗位列表、明确当前岗位或启动时冻结的本地 spec 岗位清单。messageRefs 绑定已确认正文的版本/哈希。inputRefs 留存用户要求的来源说明，供审计使用，不能当作机器证明真实用户批准的安全令牌。

**4. 核心调用链。** 自然语言及适用对话 → Agent 读取 Skill 和岗位 spec → 生成任务草稿 → 拟议公开命令 task validate → 返回有效配置/字段缺项/实质歧义 → 有效配置冻结后供方案二使用。验证仅处理本地文件，不启动浏览器。业务含义不同不得靠默认值强行补齐。

**5. 设计依据。** 复用任意支持宿主的语言理解能力，把可确定的完整性和范围检查放到程序。taskId 表示同一任务，后续仅同义改写不产生新任务；业务字段变更产生新版本，执行前重新校验受影响部分。

**6. 替代方案。** 纯 Skill 文案约束改动少但无法机械比较；CLI 内置模型增加供应商和凭据依赖；固定关键词语法只能覆盖有限表达。字段验证不能证明模型一定忠实理解用户，应由第四项直接测量。

**7. 可复述说明。** “先让 Agent 把话说成固定任务配置，再由 CLI 检查范围和授权字段；相近表达要归一到相同业务含义，缺项就明确指出。”

**8. 三个理解检查问题。**

1. 为什么“收集全部”和“只收集已有附件”不能默认视作同义？
2. 岗位 JD 为什么引用已有 spec，而不是在任务配置里再维护一份？
3. CLI 验证配置通过，为什么仍不等于证明用户意图解释正确？

审核状态：待审核。字段清单是草案；完整 JSON Schema 与字段冲突规则由实施任务编写并测试。

### 方案二：统一任务启动与安装交付

**1. 解决什么问题。** 防止不同 Agent 漏设环境变量、调用另一份 boss、混用 Skill 或账本。让用户安装配套包后，通过同一正式任务入口运行。

**2. 不用会怎样。** 版本校验能发现部分错配，但不能确保每个 Agent 都正确创建运行状态、permit 与输出目录；用户仍需检查宿主的启动细节。

**3. 核心数据结构。** 拟新增 run manifest：runId、taskId/taskHash、cliPath/version、skillPath/version、hostId/version、runDir、permitPath/hash、flowPath、ledgerRefs、status、createdAt。复用现有 permit 和 flow，不创建第二份动作日志；安装包另提供 CLI/Skill 配套 manifest 和文件校验值。首批支持矩阵记录操作系统、宿主版本、shell、Node/Chrome实测版本与宿主必需能力；未知项标为未验证。

**4. 核心调用链。** 宿主加载完整 Skill → 离线安装/版本检查 → task validate → 拟议 run start --task <文件> → 建立唯一 runDir、冻结任务与白名单、绑定 flow 与账本 → 返回 runId。后续公开业务命令明确携带 --run <runId>，入口按 manifest 加载配置并检查 taskHash；附件 worker 和 collect 路径同样绑定。宿主不需要自行拼装三组环境变量。

**5. 设计依据。** 将正式任务的配置责任交给 CLI，降低 Agent 遗漏。此方案中的“统一启动”只写本地配置，不表示自动打开浏览器、登录或获准业务操作。正式任务入口强制护栏；既有手工命令与兼容模式明确区分，不宣称该设计能阻止另一个进程绕开 CLI。

**6. 替代方案。** 只在 Skill 写启动模板改动少，但仍靠宿主完整执行；宿主专用包装器适配方便，但会形成多份策略。可以仅让包装器负责安装/进程调用，全部业务策略仍在 CLI。不支持的宿主直接报能力缺失，不偷偷改用另一种工具。

**7. 可复述说明。** “正式任务带一个 runId，CLI 自己知道该用哪份权限、状态和账本；换 Agent 也不用重新拼环境。”

**8. 三个理解检查问题。**

1. 为什么版本匹配还不足以保证护栏已启用？
2. worker 和 collect 如果不检查相同 run manifest，会出现什么缺口？
3. 应用运行上下文为什么不能被称为系统级权限隔离？

审核状态：待审核；宿主范围已明确为WorkBuddy、DeepSeek Harness。交付产物包含配套 CLI/Skill 包、无密钥安装说明、宿主能力说明；Skill 安装不能替代宿主自身允许 shell 和访问本地文件的权限。

### 方案三：固定 SOP 的逐步校验与 Agent 自由选择

**1. 解决什么问题。** Agent仍逐步选择和调用公开命令，CLI内的确定规则独立于Agent判断“当前能做哪些动作”。Agent负责简历评价、合法分支选择和材料复核；程序负责前置条件、授权、动作身份、回执与非法转换拒绝。校验器不调用模型，也不替Agent自动执行下一步。

**2. 不用会怎样。** 继续使用现有部分 flow 锁和 collect 模式门，但多岗位循环、OCR等待、消息2/3条件、收尾及局部跳过仍可能遗漏。可先采用逐步校验减小改动。

**3. 核心数据结构。** 拟在运行上下文记录当前岗位、起始页面/岗位态、冻结对象清单、当前对象、stage、materialRefs、decisionRef、pendingAction、receiptRefs、跳过原因与计数。candidateId/dataId 按入口明确区分；以入口+岗位+对应稳定ID确定对象，不混用。flow journal 是动作意图和结果的事实来源，collection ledger 保留收集状态；阶段只引用其结果，不复制出可以相互矛盾的“已发送”状态。评估提交包括对象ID、任务/规则版本、verdict及证据引用；只验证规则约束和材料完整性，不声称程序能判断所有主观评分的真实性。

**4. 核心调用链。**

- 已选路线 B，逐步校验：Agent先用拟议run status --run <ID>读取stage、allowedActions、建议下一步及阻断原因，再从允许集中选择现有公开命令，带同一runId调用。CLI在真正动作前再次根据最新状态检查，不因之前status曾允许就无条件执行。状态回执是建议与说明，不是额外授权。
- 收集：冻结岗位 → 选岗核验 → 未读快照 → 按授权核查状态 → 材料/评估或明确 collect-only → 收件/下载及回执 → 满足 SOP 与授权后发送消息2 → 保存记录 → 下一人/岗 → 收尾。全部列表搜索、接受请求等分支由任务范围及实际状态决定，不因“收集”一词自动全部启用。
- 推荐/搜索：设置并核验岗位/城市/关键词 → 冻结对象 → 预览 → OCR → Agent评估 → 合适且获授权时联系/消息，否则退出 → 下一人。消息3和附件请求保持独立动作。
- 自由权：Agent可决定需要读取哪些已收集材料、是否在授权内补充核验、提交fit/not-fit/unknown及依据、在允许退出时结束当前对象；同一阶段可以有多个合法动作。收集任务不默认改成“只评估”，也不能把跳过必需步骤作为自由选择。非必要诊断不推进业务完成数。
- 硬约束：未选定并核验岗位不能处理对象；未固定范围不能扩大候选池；未完成材料要求不能提交可触达决策；未评估fit或无授权不能联系/发消息；对象ID不一致、未知结果或全局风险暂停时禁止依赖动作。普通status只能读取规则允许的状态，不为全局暂停重新访问页面制造例外。
- 对比路线 A，程序自动推进不进入本轮实施；不提供隐式重试或自动执行直到成功的控制循环。

**5. 设计依据。** 用户明确选择B：在CLI入口限制Agent下一步，而不是把Agent替换成固定脚本。允许动作集合保留选择空间；确定的转换规则避免Agent自称条件满足即可跳步。代价是Agent仍可能停在合法阶段不再推进，因此要在方案四验证宿主能持续调用、等待异步结果和输出终止报告。

**6. 替代方案。** 仅增加 SOP 文案不能机械阻止漏步骤；内置审计 Agent 仍有模型差异及额外成本。可分阶段先完成收集，再按相同契约补推荐和搜索，不将未完成入口标为已支持。

**7. 可复述说明。** “程序告诉Agent当前允许做什么，并在执行前重新检查；Agent在允许的分支中决定怎么处理简历，不能跨越授权和状态边界。”

**8. 三个理解检查问题。**

1. 为什么固定流程能交给程序，但简历是否合适仍可能需要 Agent？
2. 进程在发送后、记结果前退出，重新启动为什么不能直接再发？
3. 程序推进和逐步校验各自保留了哪些外部 Agent 依赖？

审核状态：待审核；B路线的职责划分已于2026-11-08由用户明确选择，具体字段与接口尚未确认。OCR异步性在统一运行接口中表现为待处理材料及可查询任务状态；Agent决定何时查询，但未完成不能绕过材料门。是否复用现有任务脚本或扩展公开作业接口，实施前据宿主能力核对，不要求每种宿主都实现同一种后台shell句柄。

### 方案四：跨 Agent 与近义表达验收

**1. 解决什么问题。** 直接测量“安装 Skill、输入自然语言、完成同一业务任务”，不再用固定回放脚本通过推断任意 Agent 可靠。

**2. 不用会怎样。** 仍可证明 CLI 单项功能和合成故障处理，但无法判断宿主是否加载 Skill、是否正确解释近义表达及长期坚持流程。

**3. 核心数据结构。** 拟新增宿主适配配置、语义等价组、负对照、固定材料、独立预期任务配置/业务断言及 run report。报告保存宿主/模型/版本、Skill/CLI版本、配置、prompt、夹具版本、任务实际配置、命令与业务事件、退出原因、耗时、可用token用量和失败类别。验收期望不放入执行 Agent 可读的运行目录；评分由独立监督进程读取业务事件完成。提示词和材料冻结，避免动态线上页面影响比较。

**4. 核心调用链。** 安装包/宿主预检 → 全新隔离任务目录 → 安装或加载完整 Skill → 投递用户原始自然语言（不附详细操作答案）→ Agent 调公开测试入口 → 真实生产任务/状态逻辑 + 模拟页面适配器 → 独立验收器核对任务配置和实际事件 → 生成各宿主、各等价组报告。固定参考回放只作为环境自检，不参与 Agent 成功率。

**5. 设计依据。** 复用现有十人模拟与故障注入，增加“安装与发现 Skill”和“自然语言解释”两层。第一批样本规模草案是2个已选宿主 × 3类入口 × 每类5种等义表达 × 3次独立重复，共90轮；另计否定、缺项、歧义和越权等负对照。三类入口均需对应模拟能力，不能用推荐模拟声称收集通过。

**6. 替代方案。** 人工在三个宿主运行成本低但不可重复；自动参考回放稳定但不测试模型；直接线上测会混入账号与页面变化。本地矩阵与后续明确授权的线上验收分别记录，不能互相替代。宿主没有公开/可用的自动化入口时，记录人工验收或待验证，不模拟成已通过。

**7. 可复述说明。** “给不同 Agent 相同业务材料，用同一句话和几种同义说法分别跑，再看实际做了什么，而不是看它说完成了什么。”

**8. 三个理解检查问题。**

1. 为什么详细说明每一步的十人模拟不能证明自然语言任务理解一致？
2. 什么事件可以证明没有重复发消息，为什么最终回复不够？
3. 某宿主没有模型凭据时，该项应记录为哪类结果？

审核状态：待审核；首批宿主已确定，可接受总体完成率及预算尚未确定。越权、错人、未知结果重放和重复消息零容忍是本草案的验收条件，不是现有实测成绩。

## 10. 接口与状态设计

所有 task/run 命令均为提案，实施时需完成公开入口、参数校验、JSON回执、help与URL映射。已有合法手工命令不因本计划静默改变模式；正式任务通过明确 runId 使用新约束，不隐式猜测最近任务。

拟议顶层状态：prepared、running、waiting-evaluation、waiting-input、paused、completed、failed。waiting不是失败；缺少评估不能自动按合适处理。任务完成要求每个冻结对象有终态或明确未决项，报告不得把 paused 当作全部完成。

拟议结构化错误应携带 code、stage、runId、对象标识、attempted、outcome、evidenceRefs。run status拟返回allowedActions，每项含公开命令/子动作、必需身份和参数约束；blockedActions说明条件缺失。可选suggestedAction只作为建议，不扩大allowedActions。是否允许后续动作由固定错误分类和当前授权判定，不能由模型输出一个 retryAllowed=true 就放行。

## 11. 异常、幂等与恢复

- 禁止降级、静默回退、自动换工具。路径错误、schema损坏、版本错配、岗位/身份不明均明确停止相应步骤。
- 每次有副作用动作先写意图，结果带动作ID与证据引用。中断后的未决意图只进入核验；不自动重放。
- 普通“继续”不能恢复风险暂停或授权旧账本对账。恢复沿用现有明确岗位/范围要求。
- 接收/下载/联系/消息依据真实状态分别核验，不用本地文件存在推断平台完成；输出目录已有文件时不覆盖其他任务。
- 不增加任意重试。已明确授权的有限查看恢复与发送前确定失败规则保留各自适用条件。
- Chrome和worker异常沿用命令超时/断连回执；本计划不增加独立watchdog，也不保证所有宿主都会在超时后继续调度，后者在方案四验收。

## 12. 授权、隐私与边界

模型生成的任务配置、permit和sourceRefs均不是可信用户身份的证明；该方案仅在CLI入口限制任务行为。宿主权限与操作系统隔离独立存在。单Agent串行操作，测试不发真实消息。

默认归档仅保存必要业务字段和本地证据引用；密钥、Cookie、浏览器档案和真实简历不进入发布包或公共测试夹具。候选人内容不得修改任务授权、岗位规则或系统指令。

## 13. 性能与可观测性

复用现有截图滚轮与随机停顿，不因一致性改造改变速度。方案三每次返回有界步骤与stage耗时；分别记录页面、下载、OCR、模型评估与编排等待时间。沿用已有下载30秒等具体命令预算，不把它扩大为所有命令均30秒的承诺。

模型token与费用只在宿主提供可靠用量时计量；缺失报告为unknown。现有DSH监督用量是步骤结束后反馈，不能宣称账单硬上限。预算策略在选定宿主后确定。

## 14. 兼容、迁移、发布与撤回

先指定支持矩阵，再发行固定提交的CLI/Skill配套包与manifest，记录构建及验收回执。其他版本保持未验证，不使用“任何Agent已兼容”的措辞。

任务/运行格式独立版本；旧ledger和flow尽量复用。无法安全读取的旧任务返回不兼容错误，不自动重建或修改。撤回新功能只影响代码分发；保留原始journal和账本，不回滚已发生的业务动作。若回到旧包，未决新任务暂停、显式核验后再处理，不能用旧版绕过护栏继续。

## 16. 测试范围与通过标准

- 方案一：schema单元、等义归一、非等义负对照、缺项/冲突/提示注入边界；有效任务的业务字段与期望完全一致。
- 方案二：router/worker/collect集成、安装/版本/路径兼容、安全门回归；正式任务不能漏绑护栏。
- 方案三：三入口分别测试状态转换、材料完整性、消息条件、异常与中断恢复；关键业务断言全通过。
- 方案四：实际宿主从安装/加载Skill开始完成本地端到端任务，重复运行测量波动；固定回放、宿主执行、模拟页面、真实页面证据分开。
- 每项必选：单元、回归、异常边界与授权安全测试；本任务还需要集成、端到端和兼容测试。只评估单Agent串行行为，不把多Agent争抢浏览器加入验收要求。

## 17. 实施与测试文档交接

后续实施Agent需按每项功能生成完整测试用例并实际运行；另生成独立测试文档，包含目标、内容、前置条件、数据、步骤、预期、实际、通过标准、日志路径和未覆盖范围。实现完成未验证只能记pending-verification；全部必要验证完成才记completed。

本草案未生成完整测试用例、未执行测试、未核验远端发布状态。实施期间新增模块或实质改变职责/数据/调用链，应先更新八项说明及审核状态。

## 18. 风险与后续观察

- 任意Agent的绝对保证不可验证；支持承诺限定到能力和版本矩阵。
- task schema能验证结构与约束，不能单独证明自然语言理解正确；由语义测试测量。
- 固定流程不保证BOSS页面永不变化；真实页面覆盖与本地模拟分别归档。
- 规则明确时固定证据应稳定判断；主观评价不能用调用一致替代质量验收。
- 宿主能力不足、凭据缺失、上下文截断、后台任务等待与工具审批均可能阻断业务；报告具体阻断，不把Skill安装成功当业务成功。
- 尚无新增风险接受记录；已确认宿主清单和方案三B路线，具体模块、接口、总体完成率与模型预算仍为待审核草案。
