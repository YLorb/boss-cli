# WorkBuddy 使用 boss-cli 收集简历指南

适用读者：需要通过 WorkBuddy 执行招聘任务的招聘人员、业务负责人和部署维护人员。

这套流程由三个部分协作：WorkBuddy 按任务逐人推进，boss-cli 执行公开命令，boss-recruitment Skill 规定操作顺序、身份核验和停止条件。使用者需要提供完整 JD、任务范围和允许动作，并审核筛选结论。

建议首次使用按“环境检查 → 登录和页面准备 → 1 人试运行 → 检查结果 → 扩大到小批量”推进。在线简历处理流程为：**截图 → OCR → 本地重排去重 → Agent 一次分析 → 保存结果**。

本文更新于 2026-10-30，依据按已确认取舍整合到本地 dev 的版本。参考组合为 CLI 0.6.11、Skill 1.0.20，兼容标识为 `2026-10-30-resume-analysis-v1`。本指南还包含保留的本地 Frame 定位、OCR 分段与侧栏读取能力，不能仅凭版本号认为所有功能已部署；交付方应提供实际构建产物、完整 Skill 和功能验证说明。

## 1 明确你要收集什么

| 任务 | 完成口径 | 常见误解 |
| --- | --- | --- |
| 查看推荐或搜索简历 | 已打开、完成 OCR、保存岗位匹配分析 | 截图成功不等于评估完成 |
| 收集沟通页未读简历 | 处理本轮起始未读名单，记录结果 | 新收到的消息不会自动纳入本轮 |
| 收取正式附件 | 原文件已下载，路径、大小和哈希已核验 | 已打招呼、已求附件或已同意请求不等于已下载 |
| 主动寻访 | 按授权查看、评估、联系，并记录后续状态 | 一次寻访无法保证候选人立即回复或提供附件 |

先明确“10 份”指最多查看 10 人，还是要下载 10 份正式附件。推荐先做仅查看、不联系的试运行；需要发送消息时，另行明确触达条件和完整话术。

`collect` 是岗位账本会话，用于保存候选人记录与状态。它不会独立完成搜索新人、阅读简历、评价、发消息和下载附件；这些步骤由 WorkBuddy 按 SOP 串联。

## 2 安装与准备

### 必备条件

- 可执行本机命令、读取文件并管理后台任务的 WorkBuddy。
- Node.js 与 npm。当前包主要按 Node 24 验证，具体兼容性以交付包为准。
- 已安装的 Chrome 或兼容浏览器，以及使用者自己的 BOSS 招聘账号。
- 配套的 boss-cli 和完整 boss-recruitment Skill 文件夹。
- 可用的 OCR 服务及对简历图片上传该服务的明确授权。本指南采用 OCR 流程，因此该服务是本流程的必要条件。

不要求使用者安装 Git；可使用维护者提供的 ZIP 包。Python 不是正常招聘流程的必要依赖。Chrome 由使用者准备；缺少 Node 时先确认安装方案，不自动修改系统环境。

### 确定目录

以下是示例，需换成使用者自己的绝对路径。

| 配置 | 示例 | 用途 |
| --- | --- | --- |
| cliDir | `C:\Recruitment\boss-cli` | 唯一运行安装，含 package.json 和 dist |
| workspaceDir | `C:\Recruitment\workspace` | WorkBuddy 工作目录 |
| skillDir | `C:\Recruitment\workspace\.workbuddy\skills\boss-recruitment` | 实际加载的完整 Skill |
| runDir | `C:\Recruitment\runs\run-001` | 每轮独立记录，不覆盖上一轮 |
| ledgerDir | `C:\Recruitment\shared\ledgers` | 正式岗位账本，跨轮次固定 |
| resumeDir | `C:\Recruitment\resumes` | 已获授权下载的附件 |
| jdFile | `C:\Recruitment\jobs\server-system.txt` | 经确认的完整 JD |

按 WorkBuddy 的技能导入方式安装整个 boss-recruitment 文件夹，保留 AGENTS.md、references、scripts 和 assets 的相对关系。不要只复制 SKILL.md。路径配置文件是给 Agent 阅读的编排材料，不会自动变成 CLI 参数。

源码包先安装依赖并构建；已构建包按交付说明处理，不覆盖现有安装或重复安装环境。源码包的示例为：

```powershell
Set-Location 'C:\Recruitment\boss-cli'
npm.cmd ci
if ($LASTEXITCODE -ne 0) { throw '依赖安装失败，停止' }
npm.cmd run build
if ($LASTEXITCODE -ne 0) { throw '构建失败，停止' }
node .\dist\cli\index.js help
```

在同一执行环境完成版本检查。示例中的端口必须与本机 CLI 浏览器配置一致；53470 是当前默认值，不是所有机器都必须使用的值。

```powershell
Set-Location 'C:\Recruitment\boss-cli'
$env:BOSS_SKILL_DIR = 'C:\Recruitment\workspace\.workbuddy\skills\boss-recruitment'
$env:BOSS_BROWSER_REMOTE_DEBUGGING_PORT = '53470'
node .\dist\cli\index.js version-check --json
```

`compatible=true` 才继续。使用多个安装时核验实际 cliDir；不能因为命令都叫 boss 就认为来自同一份安装。新开的子进程须继承工作目录和环境。若 PATH 不完整，使用已核验 Node 的绝对路径，不临时换另一份运行时。

### 登录和页面准备

首次启动使用公开 `login --json`，由使用者扫码或完成验证码。之后通过 `--check-login --json` 核验；已登录则直接复用，避免重复登录。连接异常应先诊断，不能一律当作未登录并重启浏览器。

通过 `status --json` 查看当前页面、岗位和关键词。使用者可提前设置城市与岗位，再要求 WorkBuddy 保持条件。沟通页可按岗位切换 SOP 使用公开 `switch-job`，再核验 `status.chatFilterJob`；`switch-job --list` 会操作下拉菜单，不属于只读检查。按完整岗位标签唯一匹配；`collect --job` 不切换页面岗位。只读检查任务不执行切岗。

其他人的登录态、账本和 OCR 授权不随安装包转移。首次使用需明确本人的文件上传范围、服务地址、消息权限和资料保存位置。

## 3 SOP 的作用与选择

SOP 是固定执行顺序和验收条件。WorkBuddy 每轮读取实际 Skill 的 SKILL.md、AGENTS.md，再按任务加载相关规则；不要让它凭旧聊天记忆执行，也不要一次塞入所有历史日志。

| SOP | 适用场景 | 关键顺序 |
| --- | --- | --- |
| recommend-sop.md | 从推荐页查看候选人 | 岗位核验 → 列表与身份去重 → 单人预览 → OCR → 分析 → 记录 |
| search-sop.md | 搜索关键词找人 | 条件核验 → 必要时提交一次搜索 → 固定范围 → 逐人处理 |
| collect-sop.md | 沟通页起始未读名单 | 岗位核验 → 账本准备 → 一次未读快照 → 定位会话 → 读简历或收附件 |
| resume-ocr.md | 截图后的文字处理 | 输入去重 → 后台 OCR → 完整结果校验 → 重排文字与置信度 → 一次分析 |
| resume-analysis.md | 高置信度文字的结构化收集 | 编号全文 → Agent 一次字段与行号交接 → 脚本校验保存；不代替 JD 评估 |
| ledger-and-recovery.md | 正式账本与恢复 | 路径核验 → started → 操作与回执 → stop → 落盘确认 |
| non-contact-continuation.md | 明确允许单人出错后继续 | 记录错误 → 判断是否局部 → 核验列表和下一人 → 跳过失败对象 |

共同读取 tool-boundary.md、check-status.md 和 common-rules.md。具体调用参数查 invocation-guide.md；路径和页面限制查 paths.md 与 docs/boss-url-map.md。

### 推荐或搜索的标准循环

1. 保存本轮 JD、授权、人数上限和起始列表，读取历史结果去重。
2. 打开前核对当前卡片姓名与 candidateId；列表变化后不能复用旧序号。
3. `check` 明确比较页面、岗位、身份和覆盖层。只有 true 才执行依赖动作；true 不代表动作已经完成。
4. `preview` 同名同 ID，保存回执并核验 identityVerified、candidateId 和图片路径。
5. 推荐／搜索的 `preview` 截图后保持简历打开在底部，等待本人的 OCR 与一次分析结果；保存结果及时间后，按 SOP 沟通或通过公开 `back --if-open` 退出并核验列表，再处理下一人。等待期间不操作下一人。
6. 达到预算或停止条件后收尾，报告成功、待确认和失败数量。

当前已是正确搜索页且关键词正确时，复用当前状态；不要为了“初始化”再次搜索。带关键词的 `search` 会发起查询，不能称作只读检查。需要扩池时，在明确授权的上限内使用 `search-more`，按 ID 去重，不反复刷新。

### 未读及附件收集的标准循环

1. 按岗位切换 SOP 通过公开 `switch-job` 选择获准的完整岗位标签，或复用使用者已选好的岗位；WorkBuddy 读取 `status.chatFilterJob` 核验。
2. 正式收集先准备账本，再执行一次 `list --unread --json`，固定本轮姓名、dataId 和顺序。
3. 通过带姓名和 dataId 的 `chat` 定位，核验会话身份和岗位；重名不能按旧序号试点。
4. 正确会话中使用 `action resume --json` 读取在线简历；该入口截图后按远端规则等待并点击空白关闭，核验关闭回执，再按同一 OCR 流程分析。它与推荐／搜索 preview 的保持打开策略不同。
5. 按既有授权处理求附件、同意、下载与确认。先检查已发消息及附件状态，再执行对应动作。
6. 未收到附件就记等待；下载成功需核验实际文件、bytes、sha256。
7. 本人记录完成后继续起始名单下一人；最后正常 stop 账本。

打开会话使其不再未读，不需要重新拉取未读列表。发送结果不明时保存待核验状态，不补发；未加载的历史中是否已有消息，不能仅凭当前未看到来判断。

## 4 如何设计有效的提示词

一条可执行提示词应回答八个问题：从哪里开始、看哪个岗位、依据哪份完整 JD、处理多少人、允许哪些动作、保存到哪里、错误如何处理、什么算完成。

| 字段 | 建议写法 | 应避免的写法 |
| --- | --- | --- |
| 入口 | 当前搜索页，城市和岗位已设好 | 帮我找些人 |
| JD | 读取指定绝对路径中的完整 JD | 和上次差不多 |
| 数量 | 最多尝试打开 5 位，分别统计确认打开和分析完成数 | 一直找到 5 个合适的 |
| 动作 | 只查看、OCR 和分析；不联系 | 自动处理一下 |
| 输出 | 每人给证据、差距、待确认点和路径 | 给一个综合分，未定义算法 |
| 失败 | 停止受影响步骤并保存错误 | 出错自己想办法绕过去 |
| 恢复 | 读取已有回执，从明确未完成步骤继续 | 全部重跑 |

根据岗位技能、相关经验和职责评价，不使用年龄、性别等受保护属性筛选。没有约定分值时不要让 Agent 自创权重或总分；初筛意见留给使用者审核。

完整 JD 在本轮初始化时读取并保留。每人输入集中于当前岗位、当前简历重排文字、置信度及必要来源。不要反复复述 JD、读取历史截图或叠加其他人的全文。

## 5 分阶段提示词推进

以下模板可直接复制。方括号内容必须填写；模板中的授权语句仅在使用者实际同意时保留。一次明确授权后，正常流程内不需要每个动作重新确认。

### 阶段一 只检查环境

```text
使用 boss-recruitment Skill。先检查环境，不开始候选人业务。
执行目录：[cliDir绝对路径]；实际Skill目录：[skillDir绝对路径]。
核验 Node、构建产物、Skill 配套与当前登录情况；若已登录，通过公开 status 读取当前页面和岗位。
全部真实 BOSS 读取只使用已核验安装的公开 CLI。不要安装或升级软件，不点击候选人，不刷新或重置筛选。
给出可开始的条件、缺项和实际执行路径。需要扫码或手动选岗时说明具体操作。
```

### 阶段二 试运行一人

```text
使用 boss-recruitment Skill，读取完整 JD：[jdFile绝对路径]。
当前入口：[推荐或搜索]；目标岗位及城市：[完整名称]；搜索关键词：[适用时填写]。
页面条件已经设置好，先用公开 CLI 核验。最多尝试打开1位未处理候选人，仅查看和分析，不联系、不写正式账本。
运行记录：[runDir绝对路径]；历史去重记录：[绝对路径]。
允许将本轮简历图片上传至已确认的 OCR 服务：[服务地址]，由公开 ocr 命令完成。
按截图→OCR→本地重排去重→Agent一次分析→结果执行。文字优先；仅低置信度或决定性字段有疑点时核对原图，无法确认就标记待确认。不常规回读历史快照，不二次生成简历。
preview截图后保持简历打开在底部，等本人的结果保存后按SOP退出或沟通，再处理下一人。
输出匹配证据、主要差距、待确认点，以及截图/OCR/Agent/总用时；另存requestMs、reorderMs。
使用 WorkBuddy 快速模式；保存并等待后台子进程，不能重复提交正在运行的任务。
异常保存原始回执后停止依赖步骤，不重试、不切换工具、不刷新页面。
```

### 阶段三 扩大到小批量

```text
沿用本轮已确认的 JD、路径、允许动作和错误规则，再尝试查看5位未处理候选人。
读取历史回执按可靠ID去重；不重复打开已完成者，失败者保留待核对。
逐人完成截图、OCR、分析和记录后再处理下一人。当前城市、岗位和关键词保持不变。
本轮不联系、不扩池、不刷新；现有范围不足时报告实际完成数。
每人立即落盘并计时，结束分别报告尝试数、确认打开数、评估完成数和失败数。
```

需要扩池、动态列表或局部错误继续时，将其写成单独的明确条款，给出上限和适用条件。不要把“继续”理解成自动重试上一个失败动作。

### 阶段四 正式收附件

```text
按 collect-sop 收集沟通页目标岗位：[岗位完整名称和城市]。
读取完整JD：[路径]；固定账本目录：[ledgerDir]；附件目录：[resumeDir]；本轮记录目录：[runDir]。
只处理本轮首次未读快照中的前[数量]位，循环内不刷新未读。
本轮允许读取、评估、向符合已确认条件者发送求附件消息、同意附件请求、下载附件及发送收件确认。
求附件正文：[完整正文]；收件确认正文：[完整正文]。
发送前核对已有证据，发送后核验正确会话完整正文；结果不明不补发。
没有附件时记录等待，不保证本轮一定下载指定数量。核验实际文件后才记下载成功。
保持 collect 进程与 stdin，结束正常 stop 并核验落盘。独立下载与账本未同步时如实报告。
```

此模板授权了消息和附件动作。只想看简历时不要使用它；使用阶段二或三的模板即可。

### 阶段五 排障与恢复

```text
先排查这次错误：[原始错误或回执路径]，不重新执行失败业务。
检查本轮命令、子进程、输出与已有结果，区分已确认事实和待验证原因。
报告失败阶段、根因证据、最小修复方案及验证方式；不要添加回退、盲重试或换工具路径。
等待我确认修复后，再修改相关文件并做离线测试。恢复时先核验已有成果与当前页面，从明确未完成步骤继续，保持原城市、岗位和关键词。
```

“先报告、确认后修复”是本模板明确设定的节奏。如果已明确授权修复，WorkBuddy 应完成必要修改和验证，不反复询问同一许可。

## 6 一次完整示范

以下为流程演示，不是实际候选人运行结果。

使用者准备“服务器系统工程师”的完整 JD，手动选好目标城市与岗位，搜索关键词设为“GPU、硬件”。本轮仅查看 3 人，不联系。使用者发送阶段二提示词，先测试 1 人，确认结果格式和用时后再追加 2 人。

WorkBuddy 首先报告执行路径、版本兼容状态、当前搜索页及实际关键词；保存列表与历史去重依据。随后对每人执行以下逻辑：

```text
当前卡片身份核验通过
  → preview 返回同一 candidateId、identityVerified 和 PNG 路径
  → 检查同图是否已有 OCR 任务或成功结果
  → 公开 ocr 在后台运行，保留句柄并等待退出
  → completed 后读取完整重排文字与低置信度框
  → 输出证据、差距、待确认点
  → 保存分析、命令回执和时间
  → 按SOP退出当前预览，核验列表，再处理下一人
```

可用的命令示例，姓名、ID、岗位和路径均须来自当前配置或回执：

```powershell
node .\dist\cli\index.js status --json
node .\dist\cli\index.js check --page search --overlay none --job '实际岗位标签' --keyword '实际关键词' --name '实际姓名' --candidate-id '当前卡片ID' --json
# 仅在 check=true 后执行：
node .\dist\cli\index.js preview '实际姓名' --candidate-id '当前卡片ID' --json
# 路径使用 preview 回执中的完整 PNG：
node .\dist\cli\index.js ocr 'PNG绝对路径' --layout boss-online-resume --timeout-ms 120000 --json
```

推荐页使用对应 SOP 的页面和岗位检查，不照搬 search 的关键词条件。示例不是可整段无条件执行的批处理。

单人的结果模板：

```text
候选人：[实际姓名及可靠ID]
岗位匹配证据：[经历原文或紧贴原文的描述，注明来源]
主要差距：[与JD明确不一致的事实；未展示能力单列为未知]
待确认点：[缺失信息、低置信度或存在矛盾的字段]
材料：[截图、OCR结果及分析文件路径]
用时：截图[实测]；OCR[实测]；Agent[实测]；总用时[实测]
状态：[评估完成 / 待确认 / 处理失败]
```

最终报告分别列出“尝试打开、确认打开、完成评估”三种计数。假如第三人失败，不应写“已完成 3 份”，也不能直接将该人写成不匹配。

## 7 OCR 与速度优化

### 分段规则

在线简历是纵向排版，使用 `--layout boss-online-resume`。CLI 只有在原图不超过 3 MiB（3145728 字节）且高度不超过 1984 像素时直接上传；否则按文件大小与像素高度共同计算段数，沿高度均分，通常保留 256 像素重叠。全部段预检通过后才上传，完成后恢复原坐标、在共同无字间隙去重并排序。

PNG 文件大小受内容与压缩影响，不能用“宽度 × 高度”精确推出是否小于 3 MiB。每段实际编码后的字节数和高度都要合格；超限直接报错，不自动追加分段。

正式简历可能左右排版。`auto` 支持可判定的单栏或双栏，复杂表格和跨栏不保证成功。PDF、Word 不能直接传给当前 PNG OCR 入口；下载原文件后需另行明确支持的处理流程。

### 一次分析与置信度

全部必需结果成功，且退出码、候选人归属、输入哈希一致后，才提交完整重排文字。已有同图任务就等待，已有成功结果就按哈希复用，避免重复识别。

`score < 0.9` 的框记录在 lowConfidenceIds 中。按远端标准，低置信度或决定性字段存在疑点时核对原图对应区域；保留原文、分数和来源，仍无法确认的字段写待确认。needsReview=false 也不能证明没有漏行或串栏，不用高置信度替代完整性检查。

正常路径优先完整重排文字，不逐份常规读图、不回读历史快照验证正文、不让 Agent 重新生成简历。保留原图供上述疑点核验；核验不能自动触发第二次 OCR、替换算法或绕过 CLI。

### 紧凑解析交接

需要结构化收集且 OCR 成功、needsReview=false 时，按 resume-analysis.md 使用 Skill 自带的 `scripts/resume-analysis-session.mjs`：`start` 核验原图哈希并输出编号全文；Agent 一次给出字段与证据行号；`finish` 展开原文、校验并保存结果。不要每人临时编写保存程序或重复抄写整段证据。

helper 要求姓名、岗位、城市、邮箱及明确年限等字段满足既定格式；字段缺失或需要图片核验时不得猜填或修改回执来强行使用。line-map 仅适用于原文含规定标签和值的文本。此 helper 是结构化收集工具，不是岗位评分器；真实 JD 匹配仍需输出证据、差距和待确认点，不能把字段提取完成算作评估完成。

### 时间统计

| 指标 | 口径 |
| --- | --- |
| 截图 | preview 或 action resume 命令起止，含页面操作与停顿 |
| OCR | 公开 OCR 命令起止，含分段、服务请求和本地处理 |
| Agent 阅读分析 | 首次读取完整重排文字及置信度材料，到分析结果保存；包含必要的疑点原图核验 |
| 总用时 | 单人处理开始至记录完成的墙钟时间，含检查与间隔 |

紧凑 helper 的计时从 start 到 finish，含文本核验、Agent 与工具间隙和写盘，不含先前截图、下载及 OCR。远端的 30 秒目标指材料落盘后至文字提取和结构化结果完成，包含 OCR，不能用 helper 单项用时代替；这也不是所有真实简历或完整 JD 评估的耗时承诺。helper 中 ocrReused=true 表示读取成功回执，不一定是历史缓存命中。

另保存 requestMs 和 reorderMs；前者含网络、排队与识别，后者为本地校验和排序。不要重复累计子项，不把总用时写成三个阶段的简单相加，不把 Agent 用时称为纯推理时间。新任务默认每人计时；未测得的项如实注明。

一次历史诊断中，Agent 阶段为 122.191 秒，约 116.762 秒花在模型请求，最后生成报告的请求为 81.599 秒。额外读图、历史快照与未经约定的长篇评分报告扩大了任务量。因此采用一次文本分析、精简证据输出、减少无关上下文。快速模式不保证始终使用同一模型，也不能承诺固定每人耗时。

## 8 已遇到的错误与解决办法

下表区分已经落地的处理与仍待确认的问题。不能只凭相同错误提示就断言根因完全相同。

| 现象 | 已知原因或诊断重点 | 处理办法与当前边界 |
| --- | --- | --- |
| Node 找不到或 Chrome 路径发现失败 | WorkBuddy 子进程 PATH、系统环境变量或工作目录可能与人工终端不同；历史案例有对应环境缺失证据 | 核验已有 Node 和 Chrome 的绝对路径，将环境显式传给每个子进程；不修改系统权限，不直接另起 Chrome。该环境修正已用于恢复实践 |
| 后台命令还没返回就又发一次 | 未保存任务句柄，或将等待误认为失败 | 保存句柄、PID、输出与退出状态；等待原任务。同图已有成功结果按哈希复用。已有进程管理授权不等于无限重试 |
| 版本相同但行为不一致 | 执行安装、参考副本、Skill 或 dist 没有同步 | 核对实际路径、文件哈希和构建记录；版本检查通过只是必要条件。维护者同步后再执行，不能靠改版本字段消除告警 |
| 可见简历面板不唯一：0 | 表示当前检查位置没有找到可见面板，可能涉及宿主位置、加载或 DOM 变化；错误本身不能证明具体原因 | 当前代码从已核验宿主定位可见面板及直属 iframe，数量异常直接暴露；仍复现时保存上下文诊断，不扩大扫描或绕过 CLI |
| detached Frame | iframe 被替换或销毁后继续使用旧引用，或目标打开时尚未就绪 | 已增加从目标面板直接定位 Frame、检查父子归属与 detached 状态的路径。必要时使用下述明确授权的一次重开功能，不能把它当通用重试 |
| 栏内容重叠或正文有跨栏文字 | 将纵向在线简历按通用分栏逻辑处理，或框几何关系确实歧义 | 在线简历明确使用 boss-online-resume，按纵坐标分行、同行横向排序。包含、重合或归属歧义仍报错，不失败后自动切算法 |
| 小于 3 MiB 的长图仍有大面积乱码 | 文件字节数不足以约束图像像素高度；输入过长与截图质量都是排查重点 | 已增加每段 1984 像素高度限制，同时保留 3 MiB 上限及重叠。修复限制不代表所有长图都已保证识别准确 |
| 重叠裁剪导致正文重复 | 相邻片段故意覆盖相同原图区间 | CLI 恢复原图坐标，按共同无字间隙分配保留范围；无安全分界线就失败，不靠模型猜着删句 |
| 漏掉整行 | 可能是检测漏检、识别后过滤或截图遮挡；此前仅检测接口曾返回 HTTP 500，未取得足够中间证据 | 此问题尚不能宣布根因已确认或已修复。保存输入、原始响应及框坐标；经授权检查服务端日志和过滤前结果。不得用高置信度掩盖漏行 |
| 高置信度文字仍左右串栏 | 文字识别分数不衡量版面归属；表格测试中存在约 0.991 分的跨栏合并框 | 保留跨栏异常，不用置信度替代布局校验。测试中的人工表格分区不等于生产通用重排能力 |
| __name is not defined | 构建后的函数回调注入了浏览器上下文不存在的辅助符号 | 维护者检查 evaluate/waitForFunction，按项目规范改为字符串脚本，再构建并测试，不增加捕获后换路径 |
| Agent 阅读分析耗时长 | 读图与快照增加调用，输出过长及模型请求时间占比高 | 采用远端文字优先、必要疑点核验和紧凑行号交接标准；不自创评分表，不重复生成全文；按结构化收集与 JD 评估分别计时，不能外推单次样本速度 |
| 订阅侧栏能读但无法应用 | 已实现 search-sidebar 读取，尚未实现公开点击应用入口 | 能读取订阅文字不等于可执行点击；不要自行触发 DOM 事件或包装临时脚本 |
| started 正常但账本未保存或需恢复 | 未正常 stop、进程退出、已有 reading/reconciliationRequired，或外部操作尚未同步 | 保留原文件与回执，按账本恢复 SOP 处理；不新建空账本、删除锁或补发不明消息来绕过 |

### 有限重开例外

当前开发工作区提供 `preview ... --reopen-on-frame-error`。仅在用户明确允许时启用，仅适用于常规搜索页、提供 candidateId 且目标 Frame 打开失败的情况。

CLI 核验同人身份、原 URL、岗位、关键词和除 page 外的全部搜索参数，点击唯一关闭按钮一次，再打开同一人一次。身份歧义、条件变化、关闭失败、截图失败或第二次失败均停止。不刷新、不回到搜索入口、不重置条件。交付包必须实际包含该参数，不能因为本文提到就假定已安装版本支持。

## 9 失败后的标准推进方式

先保存原始命令、起止时间、退出码、stdout/stderr、候选人身份、当前页面与最后成功阶段。然后明确报告：哪些动作已成功，哪些未发生，哪些无法确认。

默认停止受影响步骤。用户明确选择仅查看不联系的局部错误继续模式时，按 Skill 区分局部与全局故障，核验原列表和下一人身份可靠后才继续。登录失效、验证码、页面不明、公共服务异常、记录无法保存时结束整轮。

用户要求修复时，先定位根因，做最小修改、构建和相关离线测试；再在授权范围内通过公开 CLI 验证。从明确未完成步骤恢复，保留原搜索条件。源码审查、离线测试通过、真实页面验收是三种不同证据，报告中分别说明。

所有真实 BOSS 操作只用已核验公开 CLI。禁止直接 CDP、其他浏览器或桌面工具、自写页面脚本、内部模块和旧 switch-job 脚本。不存在为了“只读诊断”而换工具的例外，也不添加自动回退或盲重试。

`status`、`check` 当前采用独立只读连接；`search-sidebar` 接入会话锁和页面守护。不能把所有命令统一描述成“都经过守护”，也不能把命令级锁当作整轮任务互斥。

## 10 账本与结果保存

仅查看模式保存独立评估记录，不启动正式 collect。正式业务使用跨轮次固定 ledgerDir，以完整岗位及城市为账本键，去掉薪资，预先计算 SHA-256 文件名并核验 started 返回的绝对路径。

collect 是保持 stdin 打开的常驻进程。向同一进程逐条发送 JSON，每条等待响应，不把 JSON 当作 shell 命令：

```json
{"op":"show"}
{"op":"add","job":"完整岗位名称 _ 城市","dataId":"真实会话ID","name":"实际姓名"}
{"op":"decision","dataId":"真实会话ID","decision":"PASS"}
{"op":"stop"}
```

add/decision 只在正式业务且证据支持时执行，示例 PASS 不是预设结论。candidateId 不能替代真实会话 dataId。FAIL 会移除正式记录，不能用它处理已联系待核验者。

等待 stopped 和进程退出才算正常保存。独立下载或发送不会自动回写 collect；外部结果合并按 Skill 实施，未同步时单独报告，不直接改活动账本 JSON。

建议每轮目录包含：

```text
run-001/
  task.txt              本轮完整输入、JD位置、范围和授权
  commands.jsonl        命令、起止、退出码和回执路径
  analysis.json         逐人的证据、差距和待确认点
  timing.json           四项用时及OCR子项
  receipts/             原始输出与错误
```

截图与 OCR 文件以 CLI 回执位置为准，记录关联即可。每人完成立即保存，历史去重同时检查正式账本和待关联回执。日志不保存 Cookie、Token 或密钥；对外分享指南时不附带候选人资料。

## 11 交付前验收与后续维护

首次试运行后，使用者应能回答以下问题：执行的是哪份 CLI 和 Skill；实际查看了谁；依据哪些文字得出结论；哪些消息已经发出；哪些附件真正下载；失败停在哪里；记录保存在哪里。

部署维护者交付时应提供版本组合、构建产物、完整 Skill、功能验证状态及命令说明。不要把开发者电脑路径、端口占用、浏览器登录态或未提交修复当作接收者已有的环境。升级先备份需要覆盖的文件，完成构建与相关测试，核验 Skill 内容同步，再重新检查版本和路径。

定时运行应在人工监督的小批量试运行通过后设置。固定 JD、入口、人数、允许动作和记录目录，并确认 WorkBuddy 不会重叠运行任务。同一 BOSS 浏览器只允许一个业务操作者，HR 人工操作也应错开。安装 Skill 或保存提示词不会自动创建定时任务。

本指南之外，准确参数和页面条件以交付包的公开 help、Skill 的 invocation-guide.md 和 docs/boss-url-map.md 为准；旧聊天或历史日志不能覆盖当前明确规则。
